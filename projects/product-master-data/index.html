02

PROBLEM

数据混乱的问题

分散资料、字段命名不一致与缺失语义不清，使数据难以复用、校验，也难以被AI稳定调用。

03

115 COMMON FIELDS

公司级通用字段标准

先建立跨品类可复用的公司级通用字段，统一字段名称、定义、格式与单位。

04

DATA MODEL

通用主档 + 品类专属模板

通用主档稳定承载公共信息，品类模板补充真正影响业务判断的专属参数。

05

REAL SKU PILOT

为什么选择轮胎验证

轮胎字段具有明显的结构规则、规格差异与适用性边界，适合检验数据结构是否真正可用。

使用28个真实轮胎SKU / ASIN进行验证，不用理想化样例代替真实数据。

06

COLLABORATION

真实组织落地

标准需要采购、运营及相关业务角色共同确认，才能进入真实使用。

07

USABILITY

完整不是目标，可用才是

字段不是越多越好；能够被理解、维护、校验和调用，才是有效的数据标准。

08

FINAL STRUCTURE

最终轮胎数据结构

BEFORE → AFTER｜从多表维护，进一步收敛为更适合人、系统和AI调用的数据结构。

V1｜主档 + Boom子表 + SKU汇总。V2｜品类公共参数 + 胎体 / 内胎默认规则 + ASIN / SKU差异数据；每行对应一个真实SKU / ASIN。

  • 充气 / 真空
  • 胎体类型：充气胎 / 实心胎
  • 内胎结构：有内胎TT / 无内胎TL / 不适用
  • 轮毂长度：无
  • 轮毂长度：不适用
  1. 01A｜品类公共参数
  2. 02+
  3. 03B｜胎体 / 内胎结构默认规则
  4. 04+
  5. 05C｜ASIN / SKU差异数据
09

BEFORE / AFTER

字段标准化案例

明确区分数据缺失与字段天然不适用，避免把未知值误判为0或有效业务状态。

01

充气 / 真空 → 胎体类型 + 内胎结构

把混合口径拆成可判断、可校验的两个结构字段。

02

无 → 不适用

区分数据缺失与字段天然不适用，避免把未知误判为有效状态。

03

采购成本 CNY / 销售价 USD

把采购与销售币种边界写入字段语义，避免AI混淆。

10

CALLING LOGIC

AI / RPA调用逻辑

  1. 01标准字段
  2. 02数据校验
  3. 03按任务读取
  4. 04AI / RPA调用
  5. 05明确缺失与不适用
  6. 06输出可追溯结果
11

TECHNICAL DECISION

技术路线调整

不是MySQL失败，而是根据当前业务阶段重新判断建设顺序。

  1. 01原计划：完整本地MySQL
  2. 02评估建设周期 / 数据映射复杂度 / 当前业务阶段 / 运维成本 / MCP实时取数能力
  3. 03最终策略：标准主数据先行
  4. 04MCP实时取数优先
  5. 05必要缓存
  6. 06数据库按需扩展
